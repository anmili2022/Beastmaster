# 奇盘编队实施方案

## 目标

新增独立主栏目“奇盘编队”，管理挑战斗兽奇弈前的魔兽队伍预设。预设栏位数量可选 10、12、14、15，不绑定具体盘或地图。用户打开游戏原生 `XBMPetParty` 编队界面后，通过插件悬浮小窗手动点击“应用编队”，完整替换当前队伍。

本功能与战斗中的 1/2/3 号兽笛、自动释放、借用和最后一击设置无关。

## 已确定需求

- 支持多套编队预设。
- 预设栏位数量可选 10、12、14、15，不绑定具体盘或地图。
- 预设保存有序的图鉴编号列表，内部不依赖中文名称。
- 允许少于奇盘容量，未使用位置统一位于名单末尾，不支持中间空槽。
- 宝宝下拉显示“编号 - 名称 - 兽级”；兽级只用于确认，不限制应用。
- 同一预设禁止重复宝宝。
- 预设中任一宝宝未捕获或不可用时，应用前整体中止，不做部分编队。
- 应用时完整替换当前队伍，不保留原队伍额外成员。
- 不在打开编队界面时自动覆盖；必须由用户点击“应用编队”。
- 游戏编队界面打开时显示专用悬浮小窗。
- 不直接写游戏内存，通过确认后的原生 UI/Agent 操作执行。

## 已确认读取结构

`XBMPetParty` 是右侧魔兽编队窗口。当前客户端结构：

```text
Value[5] = 当前成员数
成员起点 = 6
成员步长 = 77
成员 n 起点 = 6 + n * 77
成员块 +0 = 兽级显示
成员块 +1 = 图标 ID
成员块 +3 = 名称
图鉴编号 = 图标 ID - 242000
```

最多按 15 个位置解析。当前扫描已验证移除一只后 `Value[5]` 从 10 变为 9，加入 2 号松鼠后恢复为 10。
已确认高段第一盘的 `XBMPetParty` 容量为 12，当前队伍包含 16 螳螂、10 胡蜂、1 库西、41 蝾螈、15 壳蟹、9 巨型陆蟹、4 陆鱼、13 死魂、20 陷阱草、8 凶蛛蝎、50 贝希摩斯和 24 碧企鹅。第二盘和高段第一盘容量相同，均为 12，不能仅依据 `Value[1162]` 区分。

## 预设模型

```text
Id
Name
SlotCount
Members: List<int>
```

`Members` 长度范围为 `0..SlotCount`。列表顺序即加入顺序；由于游戏不支持手动排序，应用时通过清空后按顺序重新加入保证最终顺序。

应用时以游戏当前 `XBMPetParty` 容量为准：当前容量小于预设栏位时只应用预设前当前容量个位置，并提示用户；当前容量大于预设栏位时应用预设成员并提示空余位置数量。

## 应用流程

1. 确认 `XBMPetParty` 可见且 Ready。
2. 读取当前编队容量（支持 10、12、14、15）。
3. 按当前容量截断预设，或保留多出的空位，并提示用户。
4. 校验成员数量、编号范围和无重复项。
5. 校验所有成员已捕获并可加入。
6. 不保存恢复快照；应用失败时中止并保留已经成功加入的部分队伍。
7. 调用原生“清空整个队伍”操作。
8. 等待“确定要清空整个队伍吗？”确认窗口；只在本次应用流程主动发起清空、窗口文本匹配且未超时时确认“是”。
9. 确认成员数变为 0 后，按预设顺序逐只加入宝宝。
10. 每次操作后读取成员数和图标列表确认结果。
11. 最终名单与预设完全一致后报告成功。
12. 任一步失败立即停止并提示，保留已经成功加入的部分队伍，不自动恢复原队伍。

### 第一阶段：编队只读结构

- DEBUG 新增“魔兽编队结构”。
- 解析最多 15 个成员及顺序。
- 已完成：读取支持 10、12、14、15 栏位的编队；不依赖具体奇盘或地图名称。
- 已采集第一盘、第二盘和高段盘的成员结构；当前方案不绑定盘身份，无需继续定位盘类型字段。

### 第二阶段：栏目与预设编辑

- 已完成：新建“奇盘编队”主栏目。
- 已完成：实现预设新建、重命名、复制、删除和选择。
- 已完成：支持 `BSTPARTY|1` 文本分享与剪贴板导入，导入后生成新 ID 并处理重名。
- 已完成：预设栏位可选 10/12/14/15，允许少于容量且空位只能位于末尾。
- 已完成：下拉选择已捕获宝宝并显示缓存兽级。
- 已完成：实现重复、编号和容量校验。
- 已完成：显示当前队伍和预设逐位差异，并按容量差异提示截断或空余。

### 第三阶段：原生操作单步验证

- 已完成：开发阶段使用“记录手动编队事件”确认协议；该诊断和单步测试已从用户界面隐藏。
- 已确认“清空整个队伍”的 Agent 501 协议：`Kind=0 [2,4]` 打开成员右键菜单，`Kind=7 [0,2,0,Undefined,Undefined]` 选择清空，`SelectYesno EventParam=0` 点击“是”，随后 `Kind=8 [0]` 确认并出现 `Snapshot 0/10`。
- 已确认加入宝宝的 Agent 500 协议：`Kind=0 [7, 图鉴编号 - 1]` 将当前选中的图鉴宝宝加入编队；2 号对应 `[7,1]`，3 号对应 `[7,2]`，随后分别出现 `Snapshot 1/10|2`、`Snapshot 1/10|3`。
- Agent 500 的 `[5, n]`、`[6]` 是图鉴选择/刷新过程事件；加入操作以 `[7, 图鉴编号 - 1]` 和 `XBMPetParty` 快照变化共同确认。
- 正式功能处理清空确认时，必须处于本流程主动发起清空后的短超时窗口，并核对确认窗口文本；不得处理其他 `SelectYesno` 窗口。
- 已完成：从图鉴加入指定宝宝的 Agent/UI 协议验证。

### 第四阶段：正式应用与悬浮窗

- 已完成：按当前容量完整替换、逐步确认、中止和最终名单校验。
- 已完成：原生编队窗口可见时显示悬浮小窗。
- 已完成：悬浮窗显示当前容量、当前人数、匹配预设和“应用编队”按钮。
- 已完成：应用期间禁用重复操作，并显示当前步骤和失败原因。
- 已验证：第一盘 10 只预设实际应用成功，包含第一页/第二页宝宝、图鉴已打开时复用、清空确认和最终顺序核对。
- 已验证：第一盘 MVP 四项场景全部通过：跨第一页/第二页、图鉴未打开时自动打开、图鉴已打开时复用、少于 10 只时保留末尾空位。

应用失败时立即中止并提示，保留已经成功加入的部分队伍；不自动恢复应用前的原队伍。
